Deadzone aim is a free-aim buffer: the weapon does not instantly sit exactly on the camera center, and it does not instantly drag the whole view with every small mouse movement. Instead, the weapon is allowed to float inside a limited range relative to the center of the screen, and only after you push past that range does the view begin to turn more strongly or the weapon begin to lag visibly.


What it means
In the DoDA prototype, deadzone aim meant the gun had its own â€œlocalâ€ aim space separate from the camera. Small mouse movement moved the weapon inside a bounded box, while the actual player view only took over once that box was exceeded. That is why the effect feels like ARMA 3: the weapon has inertia, the camera is not locked to it, and there is a visible delay between where the player looks and where the weapon is pointed.


How it should feel
The important feeling is this:

the camera can keep moving,

the weapon can lag behind,

and the gun recenters or catches up gradually instead of snapping instantly.


That makes aiming feel heavier and more deliberate, especially when you are making small corrections. In ARMA-like free aim, the gun can drift away from the exact view center, and you manually â€œworkâ€ the weapon back toward the target rather than having the crosshair do everything for you.


How the prototype used it
The prototype tracked free-aim as a horizontal and vertical offset, then clamped those offsets to a maximum deadzone range. When the offset stayed inside the range, the weapon could remain visually displaced from the exact camera center. When the offset exceeded the limit, the system would start correcting or re-centering, which created the lagging-gun effect you wanted.


The prototype also tied that offset to PSprite positioning, so the weapon sprite itself visibly drifted on screen rather than merely changing an invisible math value. That is what made the mechanic feel like real free aim instead of just a hidden aim cone.


How it should work in GZDoom
In GZDoom terms, deadzone aim needs three parts:

Input accumulation. Mouse movement updates a free-aim offset instead of immediately forcing the weapon to center.

Clamp / deadzone. The offset is limited to a maximum range so the weapon cannot drift forever.

Visual presentation. The weapon sprite or overlay is offset on the screen to show the lag.


If you want it to behave like the prototype, the weapon should appear to move independently inside that zone, and the player should feel that the aim is slightly detached from the center. That is the whole point of the mechanic: the player is controlling both view and weapon alignment, but not in a perfectly locked way.


Why it matters for DoDA
For DoDA, deadzone aim is not just a gun gimmick. It supports a more tactical field mode, because the player can track targets while still feeling that the weapon has weight, stance, and handling. That makes it a good fit for an agent-based tactical game where precision, posture, and deliberate movement matter more than twitch shooting.

GZDoom does have native reload support hooks, but it does not magically give you a complete magazine system for a custom weapon by itself. The usual pattern is: use A_WeaponReady(WRF_ALLOWRELOAD) to detect the reload key, then store loaded rounds in a weapon-side variable or a dedicated ammo item, and move rounds between â€œmagazineâ€ and â€œreserveâ€ yourself.


Core idea
For DoDA, the realistic handling model should separate three things:

Reserve ammo, which lives in inventory.

Magazine ammo, which is the rounds currently loaded in the weapon.

Manipulation states, which are the visible animations: eject, insert, rack, clear jam, and ready.


That separation is what makes the weapon feel mechanical instead of arcade-like. The visible animation should not be the same thing as the ammo math; the animation is presentation, while the ammo bookkeeping is state logic.


How reload should work
A practical reload flow in GZDoom is:

Player presses reload.

Weapon enters Reload state if WRF_ALLOWRELOAD is enabled.

Weapon checks if the magazine is already full.

If not full, it ejects or transitions into an insertion state.

Reserve ammo is decremented.

Magazine ammo is incremented.

Weapon returns to Ready after the animation finishes.


If the weapon is a detachable-magazine weapon, one reload should usually mean â€œswap empty mag out, insert fresh mag, then rack or chamber if needed.â€ If it is a tube-fed or fixed-magazine weapon, the animation may represent loading one round at a time instead. GZDoom can support either model, but the gameplay logic must be authored explicitly.


Eject magazine
For a detachable magazine weapon, ejecting should be its own visible state because it matters tactically and visually. In the simplest version, ejection is only presentation plus a decrement from the weaponâ€™s loaded count to zero or partial count, depending on whether you want to preserve tactical reload behavior.

In a more realistic model:

if the magazine is not empty, the old magazine is retained in a temporary â€œheld magâ€ state,

if the magazine is empty, the weapon transitions to an empty-mag state,

the reserve count is not changed yet until the new magazine is inserted.


That is the basis for â€œtactical reloadâ€ behavior, where you can keep a partially used magazine instead of deleting it.

Insert magazine
Insertion should consume ammo from reserve and place it into the weaponâ€™s loaded-mag counter. This is the cleanest place to use a weapon-side variable such as LoadedRounds, because the weapon itself needs to know how many rounds are currently ready.


A typical sequence is:

play the insertion animation,

set or update the loaded count,

then decide whether a rack is needed.

If you want the game to model partial reloads, the inserted mag can be any size up to the weaponâ€™s max capacity. If you want a simpler game, every mag can be treated as full and only the reserve count matters.


Rack slide / chamber round
Racking is a separate operation from inserting a magazine when you want realism. It is the action that chambers a round after a fresh mag is inserted, or after a jam is cleared, or after an empty weapon is reloaded.

In practice, the rack state should:

optionally consume one chambered round if you model that separately,

end in Ready,

and be required only when the weapon is in an â€œempty chamberâ€ condition.


This matters because a weapon with a magazine inserted is not always immediately ready to fire in a realistic model. The rack is what turns â€œloadedâ€ into â€œfight-ready.â€

Clear jam
A jam clear should be a recovery state, not just another reload animation. The weapon should enter a jam state when a jam condition is triggered, then the clear-jam sequence should forcibly return the weapon to a usable state afterward.

A clean model is:

ClearJam plays the manipulation animation,

if the weapon has a loaded mag and chamber state, it returns to Ready,

if not, it falls back into Reload or Empty handling.


This makes jams feel like problems the player has to resolve, not just a cosmetic interruption.

Movement primer
DoDA movement should treat the player as having discrete body states: standing, crouched, prone, and vaulting. Each state should change how the player moves through the world, how quickly they can aim, how stable their aim is, and how easily they can fit through space. That gives the game readable tactical movement instead of one universal movement mode.


State intent
Standing is the default combat posture.

Crouch is the lower-profile controlled posture.

Prone is the lowest-profile stealth or stability posture.

Vault is a traversal action for crossing low obstacles or barriers.


Each posture should trade mobility for control or concealment. Standing should be fastest and most flexible, crouch should reduce speed but improve stability, prone should minimize exposure but severely reduce mobility, and vault should temporarily override normal control to get the player over geometry cleanly.


Aim behavior
Aim should change with posture in a way the player can feel immediately.

Standing: normal aim speed, normal sensitivity, lowest stability.

Crouch: slightly slower aim speed, slightly reduced sensitivity, improved accuracy or recoil control.

Prone: slowest aim speed, lowest sensitivity, highest stability.

Vault: aim should usually be restricted or softened during the vault animation so the movement reads clearly.


For the Space, it is best to separate aim speed from aim sensitivity. Aim speed is how fast the weapon/camera can be rotated by the playerâ€™s input, while sensitivity is the input multiplier applied before it reaches the aim logic. That gives you more control over how posture changes feel without making the controls unpredictable.

Movement speed should follow the same posture hierarchy.

Standing: full walk/run speed.

Crouch: reduced speed, useful for precision or stealth.

Prone: much slower crawl speed.

Vault: short forced movement with no free locomotion until the vault ends.


A useful design rule is that crouch and prone should not just slow the player; they should also change the way the playerâ€™s acceleration and turn control feel. That keeps posture meaningful even when the player is not firing.

Native-first boundary
GZDoom already has a large native surface: actor collision, player/pawn behavior, weapon state flow, events, CVars, and thinker lifecycles. Custom code should compose with or extend those systems, never recreate them merely because the custom feature is more complex.


For example, DoDA should use the existing crouch support as its baseline, then add only the missing prone transition, posture modifiers, and validated vault behavior. Likewise, the firearm model should use ordinary weapon states and existing reload pathways where appropriate, while DoDA weapon classes own the additional magazine, chamber, slide, and malfunction state .

Source-of-truth rule
Before I provide any code for this Space, the proposal must identify one of four implementation layers:

Layer	Use it for	Rule
Existing GZDoom feature	Built-in behavior already supported by g4.14.2	Use the native API; do not duplicate it
ZScript data class	Weapon, pawn, inventory, actor-specific persistent data	Use documented inheritance and scope
ZScript play logic	Gameplay state, input dispatch, maps, UI-facing behavior	Use one clearly assigned owner
Fork C++	A capability unavailable through documented ZScript or required engine/device integration	Prove the native/ZScript gap first
ZScript classes inherit from a base class and are scoped objects, so class choice and scope must be established before defining state or methods. Method declarations require an exact return type and typed arguments, and overridden methods must match the engineâ€™s actual signature rather than a guessed variant.


One owner per system
The new Space should enforce an ownership map:

Input dispatcher owns interpretation of doda.* input events.

Player pawn/controller owns posture transitions, collision-size changes, and posture movement modifiers.

Weapon instance owns magazine, chamber, slide, and jam state.

Vault controller validates obstacle and landing conditions, then owns the short traversal state.

Native engine owns core movement collision, use-line resolution, weapon switching, rendering, and save infrastructure unless a verified fork extension changes one of them .

This prevents the specific class of bug where an EventHandler, a pawn tick, and a weapon tick all write to velocity, stance, or ammo in the same tic.
